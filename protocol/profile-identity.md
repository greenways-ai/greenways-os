# Greenways profile identity

Status: daemon-owned identity custody and portable recovery slice for issues #51 and #114.

## Authority

`greenwaysd` owns one profile identity for a Greenways home. Greenways Desktop, the CLI, Greenways Server, and the Chrome bridge are clients of that authority; none of them owns or receives its private key.

```text
greenways-admin identity create
          │
          ▼
operating-system keyring
  private P-256 key bytes
          │ opaque handle
          ▼
greenwaysd private metadata
  self-signed public identity card
          │
          ├── identity.status
          └── identity.public-card
```

Identity creation, recovery export, and headless recovery are offline while `greenwaysd` is stopped so the administrator and daemon never become concurrent metadata writers.

## Public card

The public identity card is:

```json
{
  "protocol": "greenways-signed-profile-identity/0-alpha",
  "subject": {
    "protocol": "greenways-profile-identity/0-alpha",
    "id": "identity/…",
    "handle": "river.studio",
    "keyId": "sha256:…",
    "algorithm": "p256-sha256-fixed",
    "publicKey": {
      "kty": "EC",
      "crv": "P-256",
      "x": "…",
      "y": "…"
    },
    "createdAtUnixMs": 1
  },
  "subjectRoot": "sha256:…",
  "signature": "…"
}
```

`keyId` covers the exact closed public-key record. `subjectRoot` covers the exact typed subject:

```json
{
  "protocol": "greenways-profile-identity-subject/0-alpha",
  "identity": { "…": "the complete public identity card" }
}
```

The signature is a fixed-width P-256 ECDSA signature over those subject bytes.

## Key custody

The private key is generated by the daemon identity crate and stored as PKCS#8 bytes in the operating-system credential store under a random opaque handle. The private daemon metadata file stores that handle but not the key bytes. The public card, status projection, CLI output, Flutter clients, Chrome extension, request receipts, logs, and remote services never receive the handle or private key.

The first production backends are macOS Keychain, Windows Credential Manager, and Linux Secret Service. A headless Linux Server needs an explicit production credential backend where Secret Service is unavailable; there is no plaintext fallback.

## Portable recovery artifacts

Recovery uses two separate, closed, bounded files:

```text
greenways-profile-identity-recovery/0-alpha
  reviewed AES-256-GCM algorithm
  creation time
  exact signed public identity
  random 96-bit nonce
  authenticated ciphertext containing only the PKCS#8 private key

greenways-profile-identity-recovery-key/0-alpha
  exact SHA-256 digest of the package bytes
  one random 256-bit recovery key
```

The public identity, package header, and nonce are authenticated as AEAD associated data. The key envelope opens exactly one byte-for-byte package; package or key substitution fails before any Greenways home or keyring mutation. Both files use create-new semantics and mode `0600`. The recovery key is never accepted as a literal command-line value and is never printed in JSON, logs, receipts, Flutter state, browser storage, or diagnostics.

An existing installation exports the pair only while `greenwaysd` is stopped:

```text
greenways-admin identity recovery-export \
  --package /private/location/profile.recovery.json \
  --recovery-key /different/private/location/profile.recovery-key.json
```

Export verifies the active key/public-card binding and does not alter the identity. A headless fresh home imports the same pair while its daemon is stopped:

```text
greenways-admin identity recover \
  --package /private/location/profile.recovery.json \
  --recovery-key /different/private/location/profile.recovery-key.json
```

Recovery validates both files, their exact digest binding, AEAD authentication, signed public card, PKCS#8 encoding, and private/public key equality before mutation. It generates a fresh opaque operating-system keyring handle, writes the key only to that keyring, restores the exact prior signed public metadata with no-overwrite semantics, verifies the imported binding, and rolls back the new key entry if metadata persistence fails.

Greenways Desktop exposes the same import core through a no-argument `recover-identity` setup operation. The Rust companion owns the two fixed macOS file-selection prompts and decrypted bytes; Dart receives no selected path, package byte, recovery key, private key, keyring handle, signature, or subject root. Cancelling either prompt is non-mutating.

This is recovery of the exact profile identity, not generic private-key export, key rotation, replacement, revocation, Hestia membership recovery, or a browser credential backup.

## Local operations

The first read-only operations are:

```text
identity.status
identity.public-card
```

Both require an enrolled, authenticated local session. The browser bridge may read the public identity card because later pairing flows need public identity evidence. It cannot inspect authority inventories or private key custody internals.

If no identity exists, `identity.status` reports `unconfigured` and `identity.public-card` returns `identity-unconfigured`.

## Signing vocabulary

The daemon-owned key signs exactly five closed subject protocols:

```text
greenways-profile-identity-subject/0-alpha
greenways-application-approval-subject/0-alpha
greenways-application-revocation-subject/0-alpha
greenways-capability-grant-subject/0-alpha
greenways-capability-revocation-subject/0-alpha
```

Each signing method constructs and validates its complete typed body immediately before loading the private key. The public Rust surface does not accept arbitrary bytes, algorithms, key handles, or caller-selected subject protocols.

It does not expose:

```text
identity.sign
crypto.sign
key.export
key.handle
credential.read
kernel.eval
```

Node enrolment, source mandates, application grants, and MCP pairing must each add a separate closed record type, validator, policy decision, and receipt. Profile recovery is limited to the exact encrypted package/key protocols above and must not be generalized into arbitrary-byte signing or key export.

## Migration

The existing browser controller identity remains a compatibility source until a later migration performs:

```text
prepare
→ validate the browser public identity and exact source records
→ create or select the daemon identity
→ issue replacement typed mandates
→ commit daemon authority
→ write a migration receipt
→ disable browser-resident writable authority
```

A daemon disconnect after cutover is an unavailable state, not permission to revive a second writable identity.
