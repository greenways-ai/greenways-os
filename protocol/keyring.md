# Greenways Keyring protocol

Status: first local product slice  
Protocol: `greenways-keyring/1`

## Purpose

Greenways Keyring is the root local authority for keys used by Greenways OS. It separates ownership of credentials from the packages that request work.

A package may be authorised to ask for a typed operation. It must not receive the underlying key material.

```text
package or Greenways-enabled site
        │ typed request + declared context + limits
        ▼
Greenways OS capability broker
        ▼
Greenways Keyring
        │ signs or calls an allowlisted provider
        ▼
result / signature / receipt
```

The first implementation provides local key creation and provider-profile management. External request forwarding is deliberately deferred until origin grants, budgets, approvals, and audit receipts are implemented.

## Key classes

### Controller key

The controller is the durable key for the browser profile.

- algorithm: ECDSA P-256 with SHA-256;
- generated by Web Crypto with `extractable: false`;
- retained in the extension’s local IndexedDB identity record;
- used for Greenways identity cards, actions, personal-chain inclusions, and later package approvals;
- only its public JWK, identity ID, handle, key ID, algorithm, and creation time are projectable.

The controller is not cleared by “lock provider session”. Recovery and rotation require their own explicit, signed protocols; a UI reset must never silently replace it.

### Provider profile

A provider profile is a session-scoped credential for a model provider.

```json
{
  "protocol": "greenways-keyring/1",
  "id": "openrouter.personal.ab12cd34",
  "provider": "openrouter",
  "label": "Personal coding",
  "secret": "<session-only credential>",
  "createdAt": "2026-08-06T00:00:00.000Z"
}
```

The current allowlist is `openrouter`, `openai`, and `anthropic`.

Provider records are stored only under the extension’s `chrome.storage.session` area. They are removed when the browser restarts or the extension is reloaded, disabled, updated, or explicitly cleared. They must not be copied into IndexedDB, Hara state, app manifests, URLs, logs, analytics, project files, or exports.

### Tahto device key

Each approved Tahto origin has a distinct non-extractable P-256 device key in
the durable identity store. Pairing is a two-phase ceremony:

1. Greenways OS sends the one-time invitation, proposed device ID and public
   key to `/tahto/v1/pairing/prepare`.
2. Tahto persists and returns the exact closed `tahto.pairing-intent/1` plus
   its canonical SHA-256 digest.
3. The keyring verifies that the intent binds the proposed origin-specific
   key, device and digest, then signs
   `tahto.pairing-intent/1\n<digest>` using the same private key.
4. Greenways OS sends the unchanged intent and signature to
   `/tahto/v1/pairing/complete`, and binds the returned node/device identity
   only after successful completion.

The invitation token is never stored by Greenways OS. Tahto receives no private
key, and pairing returns no administrator role or application grants. Exact
prepare and complete retries are safe after a lost response.

## Public status projection

`status()` returns:

```json
{
  "protocol": "greenways-keyring/1",
  "controller": {
    "identityId": "identity/...",
    "handle": "river.studio",
    "keyId": "sha256:...",
    "algorithm": "ECDSA-P256-SHA256",
    "createdAt": "..."
  },
  "providerProfiles": [
    {
      "protocol": "greenways-keyring/1",
      "id": "openrouter.personal.ab12cd34",
      "provider": "openrouter",
      "label": "Personal coding",
      "createdAt": "...",
      "sessionOnly": true
    }
  ],
  "providerCredentialStorage": "session"
}
```

The projection never includes a private `CryptoKey`, public-key storage handle, provider credential, encrypted credential blob, or credential prefix.

## Local operations

The first implementation supports:

- create the controller when no controller exists;
- inspect public keyring status;
- add one session provider profile;
- remove one session provider profile;
- clear all session provider profiles;

Duplicate profile IDs, unsupported providers, malformed records, multiline credentials, and replacement of an existing controller fail closed.

## Future capability operations

The external protocol should expose operations, not secrets:

```text
key/public
key/sign
model/list
model/generate
model/cancel
```

A future `model/generate` request must include an exact caller origin or package ID, selected profile, model, disclosed context summary, byte/token limits, maximum cost, timeout, and request ID. The keyring host should independently enforce provider/model allowlists, budgets, rate limits, and cancellation.

The following operations are forbidden:

```text
key/get
key/export-private
credential/get
credential/list-raw
http/arbitrary-request
chrome/call
eval
```

## Browser trust boundary

All packaged extension pages share one Chrome extension principal. Internal modules and Hara contexts provide lifecycle discipline, not a browser-enforced sandbox against compromised bundled code. Therefore:

- remote executable code is forbidden;
- the keyring host and package catalogue must be reviewed together;
- highly privileged future DevTools may require a separate companion extension;
- a native companion may later move durable secrets into the operating-system keychain.

The website-facing bridge must use exact origin allowlists and typed messages. A website must never be able to submit an arbitrary URL, authorization header, HTTP method, or provider payload that would turn Greenways Keyring into a general cross-origin proxy.
